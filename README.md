# Multi-GPU бенчмарк двумерного стенсила: принципы работы, алгоритмы и распараллеливание

Документ описывает два компонента проекта: вычислительный бенчмарк и скрипт визуализации.
Бенчмарк параметризуется размером сетки (`dim`, список значений) и типом данных
(`float`/`double`), что позволяет исследовать масштабирование в зависимости от объёма
задачи и арифметической интенсивности.

| Файл | Назначение |
|---|---|
| `stencil_bench.cu` | CUDA + OpenMP бенчмарк: шаблонное численное ядро (`float`/`double`), обмен граничными данными, замеры времени, выгрузка CSV |
| `plot_benchmark.py` | Python-скрипт: агрегация CSV по (dim, precision), пересчёт метрик масштабирования, построение рисунков (PDF/PNG) |

Общий конвейер обработки:

```text
[stencil_bench.cu]
  для каждого dim из списка:
    для каждой точности T из {float, double}:
      инициализация сетки -> для p = 1..P: warmup -> (reps x iters) шагов
      -> сборка результата -> верификация против 1 GPU (той же точности)
      -> медиана/min -> benchmark_results.csv
        |
        v
[plot_benchmark.py]
  загрузка CSV (1..N файлов) -> агрегация повторов по (dim, precision, variant, p)
  -> пересчёт S(p), E(p), overhead внутри каждой группы
  -> scaling_dim<N>_<prec>.pdf/png, overhead_dim<N>_<prec>.pdf/png, aggregated_results.csv
```

## 1. Решаемая задача

### 1.1 Численная задача: двумерная теплопроводность

Модельная задача — нестационарное уравнение теплопроводности на единичной пластине:

$$\frac{\partial u}{\partial t} = \alpha \nabla^2 u = \alpha\left(\frac{\partial^2 u}{\partial x^2} + \frac{\partial^2 u}{\partial y^2}\right),$$

дискретизованное на равномерной сетке `dim x dim` явной конечно-разностной схемой FTCS
(forward time, centered space) с пятиточечным шаблоном («крест»). Начальное состояние —
нагретый прямоугольник ($u = 1$) и две точки-источника; координаты масштабируются под `dim`.

- **Граничные условия:** Дирихле с нулевым значением за пределами области ($u = 0$ вне сетки). Реализованы нулевыми гало-строками на внешних границах декомпозиции и тернарными проверками по $x$ внутри ядра.
- **Роль задачи в бенчмарке:** стенсил — канонический представитель memory-bound нагрузок с ближними зависимостями по данным; варьируя `dim` и размер типа (`float` — 4 Б, `double` — 8 Б на ячейку), можно менять отношение объёма вычислений к объёму обмена и трафик памяти, изолируя стоимость коммуникаций.

### 1.2 Задача бенчмаркинга: сильное масштабирование при разных размерах и точностях

Измеряется **сильное масштабирование** (strong scaling): для каждой пары (dim, precision)
размер задачи фиксирован, число GPU $p$ растёт, на каждый GPU приходится всё меньший фрагмент.

- **Измеряемая величина:** среднее время одного шага схемы $T_p$ (мс) при разных $p$, `dim`, точностях и стратегиях обмена; из него выводятся ускорение, эффективность и производительность. Sweep по `dim` показывает, как рост задачи улучшает масштабируемость; sweep по точности — как удвоение трафика памяти влияет на время шага и долю коммуникаций.
- **Сравниваемые стратегии:** прямой обмен между GPU (P2P), обмен гало-строками через хост и намеренно наивная полная перекачка фрагмента через хост. Арифметика внутри одной точности идентична во всех вариантах, поэтому различия во времени отражают только стоимость коммуникаций, а результаты обязаны совпадать побитово.

## 2. Численный алгоритм и структура данных

### 2.1 Явная схема как итерации Якоби; шаблонизация по типу

Разностная схема обновляет все ячейки независимо, только из значений предыдущего шага:

$$u^{n+1}_{i,j} = u^n_{i,j} + r\left(u^n_{i-1,j} + u^n_{i+1,j} + u^n_{i,j-1} + u^n_{i,j+1} - 4\,u^n_{i,j}\right), \qquad r = \frac{\alpha\,\Delta t}{\Delta x^2}.$$

- **Итерации Якоби:** отсутствие зависимостей внутри шага (в отличие от Гаусса–Зейделя) делает схему идеально параллельной по данным. Ядро реализовано как шаблон `stencil_kernel<T>`, `T ∈ {float, double}`; коэффициент `SPEED = 0.25` точен в двоичной записи для обоих типов, поэтому схема и граница устойчивости ($r \le 1/4$) одинаковы — меняется только округление и трафик памяти.
- **Разные точности — разные численные задачи:** поля float и double расходятся из-за округления (это ожидаемо и не является ошибкой), поэтому верификация и эталонное время $T_1$ ведутся отдельно для каждой пары (dim, precision). Начальное поле хранится на хосте в double и конвертируется в `T` при загрузке (корректное округление одних и тех же значений).

### 2.2 Гало-раскладка и двойная буферизация

Каждому GPU принадлежит полоса (slab) из `local_h = dim / p` строк. Буфер содержит `local_h + 2`
строк типа `T` в **единой раскладке для всех GPU**:

```text
строка 0             <- верхнее гало: последняя строка соседа сверху
строки 1..local_h    <- собственные ячейки данного GPU
строка local_h + 1   <- нижнее гало: первая строка соседа снизу
```

- **Гало (ghost cells):** дубликаты граничных строк соседей для вычисления шаблона на краях полосы. Буфер 0 заполняется поstripно целиком (свои строки + настоящие гало + нули вне сетки); внешние гало буфера 1 остаются нулями от `cudaMemset`, внутренние доставляются обменом. Индексы в ядре — `size_t`, что безопасно для больших сеток (`dim²` может превышать `int`).
- **Ping-pong:** шаг читает `buf[cur]` и пишет `buf[cur^1]`, затем индекс инвертируется. Копирование собственного фрагмента не нужно: ядро перезаписывает все свои строки, а обмен доставляет гало сразу в буфер, который станет входным на следующем шаге. Итоговое состояние — в буфере `(warmup + reps*iters) & 1`.

## 3. Методы распараллеливания

Два уровня параллелизма: массовый параллелизм по данным внутри GPU (CUDA)
и параллелизм по подобластям между GPU (OpenMP-потоки как хостовые координаторы).

### 3.1 Уровень GPU: CUDA-ядро стенсила

Один CUDA-поток вычисляет одну ячейку; блоки `32 x 8`, сетка блоков
`((dim+31)/32, (local_h+7)/8)`; индекс строки `y = 1 + blockIdx.y*blockDim.y + threadIdx.y`
сразу попадает в собственную область — гало-строки не пересчитываются.

- **Коалесцированный доступ:** варп (32 потока) вытянут вдоль $x$ — обращения к глобальной памяти сливаются в минимальное число транзакций; соседи по $y$ переиспользуются через кэш. Для `double` транзакций вдвое больше при том же числе потоков.
- **Характер нагрузки:** ~7 FLOP на ячейку при минимуме $2\,\mathrm{sizeof}(T)$ байт трафика (8 Б для float, 16 Б для double): арифметическая интенсивность $\lesssim 1$ FLOP/байт (float) и $\lesssim 0.5$ (double). Оба варианта упираются в пропускную способность памяти, поэтому на больших сетках время шага для double ожидается примерно вдвое больше, чем для float.

### 3.2 Уровень узла: декомпозиция домена и OpenMP

Область режется **одномерно по строкам** (slab decomposition): GPU $d$ владеет строками
`[d*local_h, (d+1)*local_h)`. Выбор 1D-декомпозиции вместо 2D:

- **Минимум соседей и транзакций:** не более двух соседей, строка непрерывна в памяти — один `memcpy` на границу за шаг. Объём обмена $O(\mathrm{dim}\cdot\mathrm{sizeof}(T))$ против вычислений $O(\mathrm{dim}^2/p)$: с ростом $p$ отношение поверхности к объёму растёт и ограничивает эффективность; с ростом `dim` — падает.
- **Потоковая модель:** один OpenMP-поток на GPU (`num_threads(p)`, `cudaSetDevice` в каждом), координация через `#pragma omp barrier`; `omp_set_dynamic(0)` фиксирует число потоков. Конфигурации с `dim % p != 0` пропускаются с пометкой, а не завершают программу — при sweep размеров часть конфигураций может быть недоступна.

## 4. Обмен граничными данными и синхронизация

### 4.1 Три режима обмена

После шага каждый GPU отправляет соседям крайние строки и получает их строки в свои гало.
Объёмы указаны на один GPU за шаг ($s = \mathrm{sizeof}(T)$: 4 Б float, 8 Б double):

| Режим (variant в CSV) | Путь данных | Объём на GPU за шаг | Барьеров на шаг |
|---|---|---|---|
| `stencil_p2p` | GPU $\to$ GPU, `cudaMemcpyPeerAsync` (NVLink/PCIe P2P) | $2\,\mathrm{dim}\cdot s$ (16/32 КиБ при dim=2048) | 1 |
| `stencil_host_halo` | GPU $\to$ pinned-буфер хоста $\to$ GPU | 2 строки D2H + 2 строки H2D | 2 |
| `stencil_host_full` | весь slab через хост (антипример) | $2\,\mathrm{dim}^2/p \cdot s$ (16/32 МиБ при dim=2048, p=2) | 2 |
| `stencil_single` | обмена нет (1 GPU, эталон) | 0 | 0 |

- **P2P:** доступность проверяется `cudaDeviceCanAccessPeer` для всех пар, включается `cudaDeviceEnablePeerAccess`; при недоступности режим пропускается. Для double сообщения вдвое крупнее — на латентно-доминирующем режиме (малые `dim`) разница мала, на полосно-доминирующем (большие `dim`, быстрый линк) время обмена растёт почти вдвое.
- **Host-варианты:** staging-буфер в page-locked памяти (`cudaHostAlloc`), типизирован под `T`. `host_full` передаёт в $\mathrm{dim}/(2p)$ раз больше данных, чем гало-обмен (512× при dim=2048, p=2), — демонстрация цены наивной организации обмена.

### 4.2 Синхронизация и инвариант корректности

Структура одного шага (для $p > 1$):

```text
stencil_kernel<T><<<grid, block>>>(buf[cur^1], buf[cur]);  // пересчёт своих строк
cudaDeviceSynchronize();                                   // строки готовы к отправке
обмен: крайние строки buf[cur^1] -> гало buf[cur^1] соседей
#pragma omp barrier                                        // все гало доставлены
cur ^= 1;                                                  // локально в каждом потоке
```

- **Инвариант «пиши в следующий буфер»:** обмен записывает только в `buf[cur^1]` соседа — тот ещё может читать `buf[cur]`, гонок нет; барьер гарантирует доставку всех гало до старта следующего ядра. Схема остаётся синхронным Якоби во всех режимах, поэтому внутри одной точности результат побитово совпадает с 1 GPU (`max_diff = 0`).
- **Дополнительные барьеры host-пути:** два барьера — после записи своего слота в staging-буфер и после чтения чужих слотов (до перезаписи на следующем шаге). На 1 GPU синхронизация внутри шага не нужна: порядок обеспечивает один CUDA-стрим, `cudaDeviceSynchronize` — только в конце замера.

## 5. Методика измерений и метрики

### 5.1 Протокол замеров и верификация

Полный прогон — sweep: для каждого `dim` из списка и каждой точности выполняются все
конфигурации ($p$, режим) по протоколу: `warmup` шагов (прогрев JIT, кэшей, частот) $\to$
`reps` повторов по `iters` шагов; время шага повтора $=$ wall-time / `iters`; старт выровнен.

- **Статистика:** медиана (основная метрика) и минимум по повторам; разброс min–median визуализируется усами. CSV: `variant, precision, gpus, dim, iters, warmup, reps, median_ms, min_ms, mcells_s, speedup, efficiency_pct, max_diff` — колонка `precision` (`float`/`double`) входит в ключ группировки при анализе.
- **Верификация по группам:** эталонное поле и $T_1$ свои для каждой пары (dim, precision); первый прогон группы — 1 GPU. Каждый вариант сверяется поэлементно с эталоном своей точности: ожидается побитовое совпадение (`max_diff = 0`), любое отличие — предупреждение. Поля разных точностей не сравниваются: их расхождение — накопленное округление, а не ошибка.

### 5.2 Метрики масштабирования

Внутри каждой группы (dim, precision) по медианному времени шага $T_p$:

$$S(p) = \frac{T_1}{T_p}, \qquad E(p) = \frac{S(p)}{p}\cdot 100\%, \qquad \mathrm{Throughput}(p) = \frac{\mathrm{dim}^2}{T_p},$$

$$T_{\mathrm{ideal}}(p) = \frac{T_1}{p}, \qquad T_{\mathrm{over}}(p) = \max\!\left(0,\; T_p - \frac{T_1}{p}\right), \qquad \phi(p) = \frac{T_{\mathrm{over}}}{T_p}.$$

- **Модель эффективности:** если $T_p \approx T_1/p + c$ ($c$ — почти константное время обмена, доминирует латентность), то $E(p) \approx (1 + p\,c/T_1)^{-1}$: эффективность растёт с `dim` (больше вычислений на тот же обмен) и падает с $p$. Для double $T_1$ примерно вдвое больше при том же $c$ (латентность) — эффективность гало-обмена оказывается выше, чем для float; это ожидаемый эффект, а не аномалия.
- **Пропускная способность и сверхлинейность:** минимальный трафик $2\,\mathrm{dim}^2 s$ за шаг даёт оценку эффективной ПС $B(p) = 2\,\mathrm{dim}^2 s / T_p$ для сравнения с пиковой ПС памяти GPU (roofline). При малых `dim` фрагмент может целиком поместиться в L2 и дать $T_p < T_1/p$; отрицательные накладные расходы обнуляются и помечаются в отчёте.

## 6. Визуализация результатов (`plot_benchmark.py`)

### 6.1 Загрузка и агрегация данных

Скрипт принимает один или несколько CSV, поддерживает новый формат (с колонкой `precision`)
и legacy-формат (`avg_ms` $\to$ `median_ms`, `precision = float` по умолчанию).

- **Агрегация:** группировка по (`dim`, `precision`, `variant`, `gpus`): медиана времён, минимум минимумов, максимум `max_diff`, счётчик `n_runs`. Метрики $S(p)$, $E(p)$, $T_{\mathrm{over}}$, $\phi$ пересчитываются от эталона $T_1$ внутри каждой группы (dim, precision) — данные разных точностей никогда не смешиваются.
- **Контроль:** в stdout — сводная таблица по каждой группе и проверка корректности (`max_diff` против нуля); объединённые данные — в `aggregated_results.csv`.

### 6.2 Рисунки и оформление

Для каждой пары (dim, precision) строятся два рисунка:

- **`scaling_dim<N>_<prec>`** — панель $2\times2$: (а) время шага $T_p$ в лог-масштабе с усами min–median; (б) ускорение $S(p)$ против идеальной прямой; (в) эффективность $E(p)$ против 100%; (г) производительность против идеальной линейной зависимости. Общая точка $p=1$ из эталона группы.
- **`overhead_dim<N>_<prec>`** — сгруппированные столбцы по $p$: (а) доля обмена $\phi$, %; (б) абсолютная оценка $T_{\mathrm{over}}$, мс (лог-шкала). Сравнение рисунков float/double одного `dim` показывает, как удвоение трафика меняет баланс вычислений и коммуникаций.

Оформление — под ч/б печать и русскоязычную публикацию: маркер + тип линии + уровень
серого + штриховка (без цвета); подписи на русском; LaTeX (`T2A` + `babel-russian`)
с автоматическим переходом на mathtext/DejaVu Serif; PDF + PNG 300 dpi; ширина 7.2″
(меняется `--width`). Точность указывается в заголовке каждого рисунка.

## 7. Сборка и запуск

### 7.1 Бенчмарк

```bash
nvcc -O3 -Xcompiler -fopenmp -arch=native stencil_bench.cu -o stencil_bench

# аргументы: dims iters reps warmup types
# полный sweep: три размера, обе точности
OMP_NUM_THREADS=8 OMP_PROC_BIND=spread OMP_WAIT_POLICY=ACTIVE \
    ./stencil_bench 2048,4096,8192 200 7 20 float,double

# только double на одной сетке:
./stencil_bench 4096 200 7 20 double
```

Результат — таблица в stdout и `benchmark_results.csv` (колонка `precision`). Сначала
проверяйте `max_diff`: внутри точности ожидается ровно 0; ненулевые значения означают
некорректную конфигурацию. Память хоста: $3\,\mathrm{dim}_{max}^2 \cdot 8$ Б (при 8192 —
1.5 ГБ); память GPU на device: $2(\mathrm{local\_h}+2)\,\mathrm{dim}\cdot s$ на буферную пару.

### 7.2 Визуализация

```bash
pip install numpy pandas matplotlib

python plot_benchmark.py benchmark_results.csv -o figures
# несколько прогонов объединяются перечислением:
python plot_benchmark.py run1.csv run2.csv run3.csv -o figures

# полезные опции:
#   --width 3.4      одноколоночный рисунок
#   --formats pdf    только вектор
#   --dims 4096      фильтр по размеру сетки (обе точности)
#   --no-latex       принудительный mathtext
```

Для полноценного LaTeX-рендеринга кириллицы нужны `texlive-lang-cyrillic`, `cm-super`,
`dvipng`; без них скрипт сам перейдёт на mathtext. Комплекты рисунков создаются отдельно
для каждой пары (dim, precision), например `scaling_dim4096_float.pdf` и
`scaling_dim4096_double.pdf`.
